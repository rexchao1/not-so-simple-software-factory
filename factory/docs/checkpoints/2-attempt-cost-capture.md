# Checkpoint 2: Attempt cost capture

Source: frozen PRD `state/checkpoints/factory/2.md` in chao-orchestrator, frozen 2026-09-04.

## Slice
After this checkpoint, every Pipeline stage and every attempt that ran under the Claude Code runtime carries the dollar cost, the token usage, and the per-model breakdown Claude reported, and the run detail shows all three on each stage and on each attempt.
The worker's result capture keeps `total_cost_usd`, `usage`, and `modelUsage` from Claude's final result event, the supervisor hands them to the worker manager with the exit message, the stage completion request carries that stage's values to the server, the manager adds them up across the attempt's stages, and the attempt completion request carries the sum on every path an attempt can complete by.
A Claude Code stage that exits without a cost, without usage, without a model breakdown, or with all of them zeroed is logged as a warning on the worker, so a change in Claude's output shape is visible in the worker log rather than as an empty column.
A migration adds nullable cost, token, and model columns to the attempt row and to the stage row, and the JSON at `GET /api/v1/runs/{run_id}` and `GET /api/v1/attempts/{attempt_id}` shows `cost_usd`, `usage`, and `models` when they were measured and omits them when they were not.
Which models were used is read from the keys of `models`: a stage names the models it saw, and an attempt names every model across its stages with the per-model totals, and no model name lives in factory code or configuration.
An attempt run by Codex, Pi, or the fake cloud backend shows nothing, the same as every attempt today.
A Go test proves each of those, a migration test proves attempts and stages that already ran stay unmeasured rather than reading as zero, and a claim test proves a worker can still claim after the migration.
The Go tests are the acceptance evidence for this checkpoint; the orchestrator gets no new reader here.
The orchestrator's `bin/checkpoint-cost` reading the measured cost, the per-checkpoint sum over the runs it submitted, and a `bin/factory-status` mode that shows the run JSON are a later checkpoint in chao-orchestrator.

## Decisions
D1. Claude's final result object carries `total_cost_usd` as a number, `usage` as an object with `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, and `output_tokens`, and `modelUsage` as a map from model name to an object with `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costUSD`, `contextWindow`, and `costBasis`; the last `result` line of `--output-format stream-json`, which is what `internal/worker/supervisor.go:232-238` runs with the prompt on standard input and no `--input-format`, carries the same fields under the same names as the `--output-format json` result; and `usage` and `total_cost_usd` on that line are the total for the whole call, not the last turn. Cited: orchestrator session note 2026-09-04, quoting code.claude.com/docs/en/headless, "The last line of the stream is a `result` message with the final response text, cost, and session metadata", and code.claude.com/docs/en/agent-sdk/cost-tracking, "It includes `total_cost_usd`, the cumulative estimated cost across all steps in that call", with per-turn `usage` only under `--input-format stream-json`, which the worker does not pass; `state/checkpoints/ledger.tsv:10`, `:11`, and `:13` in chao-orchestrator, where one `--output-format json` result reported `cache_read` of 812,113, 1,549,950, and 1,350,356 tokens, more than one context window holds, so the result's `usage` is a sum over every turn; `bin/checkpoint-pass:224-228` in chao-orchestrator reads the five money and count fields from that result on every planning pass; review answer 2026-09-04 to E1 and Q4, which accepted settling E1 from these sources rather than a paid run.
D2. `usage` counts only the top-level agent loop, while `total_cost_usd` and `modelUsage` include subagent requests, so the money column is `total_cost_usd`, the `models` breakdown is the count of record when the two disagree, and the stream's per-step `assistant` usage is never summed. Cited: orchestrator session note 2026-09-04, quoting the cost-tracking page, "`usage`: Excluded. Counts only the top-level agent loop", "Where you have the choice, account from `total_cost_usd` or `modelUsage` rather than `usage`", and "Per-step `output_tokens` is a placeholder, so read output tokens from the result message"; the per-turn summing branch the review draft held in reserve is dropped because that quote shows it would undercount output.
D3. `claudeResultCapture` gains `costUSD *float64`, `usage *protocol.Usage`, and `models map[string]protocol.ModelUsage`, read by a second unmarshal that is independent of the one that decides the event is a result. The existing struct at `supervisor.go:791-795` stays as it is, so the result, `is_error`, and `found` are decided exactly as today. After it succeeds, the same sanitized line is unmarshalled again into a struct of three `json.RawMessage` fields, `total_cost_usd`, `usage`, and `modelUsage`, and each raw value is decoded on its own: a `total_cost_usd` that decodes as a `float64` of zero or more sets `costUSD`; a `usage` that decodes as an object whose four counts each decode as an `int64` of zero or more sets `usage`; a `modelUsage` that decodes as an object with at least one entry, whose every entry has a non-empty key and decodes to an object whose four camel-case counts are `int64` of zero or more and whose `costUSD` is a `float64` of zero or more, sets `models`, with `contextWindow`, `costBasis`, and any other entry field ignored. A field that is absent, negative, or does not decode leaves its own value nil and never touches the result or the other values, so a malformed cost costs only the cost. A `usage` missing one of its four counts, or a `modelUsage` with one bad entry, is malformed as a whole, because a partial total would undercount without any sign of it, and D22's warning is the sign instead. Cited: `internal/worker/supervisor.go:746-752` is the struct; `supervisor.go:787-812` is the single unmarshal today, and its `line.reset(); return` at `:792-795` discards the whole event when the unmarshal fails, which is why the cost must not ride on that struct; the sanitized line keeps every byte outside the `result` string value per `supervisor.go:814-820` and `:874-880`, so numbers and the two objects survive to the second unmarshal; the model entry field names are D1's.

## Failure modes
- Claude's result event has no `total_cost_usd`: the stage and attempt complete as today, the cost stays nil, usage and models are kept if the event carried them, the worker logs `claude_cost_missing` with `which: cost`, and the JSON omits only the missing key.
- Claude's result event carries a `total_cost_usd`, `usage`, or `modelUsage` that does not decode, such as a string where a number belongs, a negative count, a usage object missing a count, or a model entry missing its cost: the result and `is_error` are captured as today, only the malformed value stays nil, the worker logs `claude_cost_missing` naming it, and the completions carry whatever did decode.
- Claude's result is the zeroed result of a session crash: the zeros are stored as measured, the worker logs `claude_cost_missing` with `which: zeroed`, and the attempt fails with Claude's message as today.
- Claude renames `total_cost_usd`, `modelUsage`, or a count in a later release: every Claude Code stage logs `claude_cost_missing`, the columns stay NULL, and the log is the one place that tells this apart from a Codex or Pi attempt.
- Claude reports `is_error: true` with a cost: the stage and attempt fail with Claude's message, as today, and the cost is stored on both.
- A Claude stage reports a cost and the attempt then fails, is cancelled, or loses its lease inside the stage loop: the stage row already holds its cost from the stage completion, the handle's sum already holds it, and the early attempt completion carries it.
- A stage is cancelled or times out before Claude prints its result: that stage stores NULL, adds nothing, and logs nothing, earlier stages' costs are still on their rows and in the sum, and the attempt completion carries the partial sum.
- A stage completion reaches the server with a negative or oversized value: the client gets 400 `invalid_cost`, the worker's stage loop treats it as a failed stage completion at `attempt_lifecycle.go:348-360` and fails the attempt, which cannot happen from the worker's own decoder because D3 refuses negatives before they are sent, and which is the right outcome for any other client sending bad money.
- Negative cost, negative token count, or oversized `models` reaches the attempt completion: the client gets 400 `invalid_cost`, the attempt stays running, and the worker logs `attempt_completion_not_recorded` at `internal/worker/attempt_lifecycle.go:848-854`.
- A new worker completes against an old server: the server rejects the unknown field with 400, the stage or attempt completion is not recorded, and the lease sweep marks the attempt `lost`; D26 and D27 order the restart to prevent it.
- An old worker completes against a new server: no cost is sent, the columns stay NULL, indistinguishable from today.
- The attempt completion is retried after the first one landed: the stored attempt comes back with its cost and nothing is overwritten.
- The stage completion is retried after the first one landed with the same values: the stored stage comes back; with different values it is `stage_not_running`, as today for a changed result.
- The attempt's lease expires before completion: the attempt is `lost`, its row has no cost, and the stage rows completed before then keep theirs.
- A Work is retried or answered: the reset stages read NULL until they run again, and every earlier attempt row keeps its own sum.
- Migration 041 fails at startup: the factory does not start, the error names the migration file, and the human sees it in the tmux session, per `internal/controlplane/store.go:546`.
- A select that feeds `scanAttempt` or `scanStageRun` is left without the six new columns: every call through it fails with a scan arity error, and for the two claim selects that means no worker can claim; the claim acceptance test catches it before merge.
- An attempt or stage that ran before the change: every cost column is NULL, and the JSON omits `cost_usd`, `usage`, and `models` rather than showing zero.
- A Codex, Pi, fake cloud, or code stage: no cost, no warning, as today.
- Claude's result string exceeds 256 KiB: the result is truncated and marked so, as today per `internal/worker/supervisor.go:801-810` and `supervisor_test.go:536-549`, and the cost, usage, and models on the same line are still captured and stored, because the bound never counts the result bytes.
- The bytes of the result line outside the result string exceed the 1 MiB supervisor line bound: the line is invalid, no result and no cost are captured, and the attempt fails with "Claude Code returned no terminal result event", as today per `supervisor.go:874-880`, `:432-433`, and `supervisor_test.go:551-558`.
- `usage` and the sum of `models` disagree because a subagent ran: both are stored as reported, and the documentation of D24 says which counts what.

## Notes
Rollout is manual: once this branch merges into main, the human brings the factory back up from Terminal.app rather than through any automation.
The server process comes back before the worker process, and both restart from the same build.
The store applies any pending migration as soon as it opens, per `internal/controlplane/store.go:501-549`, so migration 041 takes effect automatically at that restart with no separate guard added in code.
The order matters because a worker running these changes that completes an attempt against a server still on the old build gets that completion rejected with a 400 on the unknown field, so the server has to be the first process back.
